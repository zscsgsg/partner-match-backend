【伙伴匹配系统 — 智能组队平台】                    2026.03 - 至今

技术栈：Spring Boot 3.5、MyBatis-Plus、Redis、Redisson、Spring AI Alibaba、
       WebSocket、Micrometer、Prometheus、Grafana、Vue 3

项目描述：
  基于标签体系的智能组队匹配平台，用户可通过技能标签描述自己，系统自动推荐

核心工作：

     降级 + Guava RateLimiter 限流保护（QPS=5）防止 AI 接口被打爆
  4. Redis 缓存实现穿透防护（空值缓存）+ 击穿防护（Redisson 互斥锁重建）
     + 雪崩防护（TTL 随机化），缓存命中率 85%+
  5. WebSocket 实现队伍内实时聊天室，消息持久化到 MySQL，支持历史消息分页查询
  6. Micrometer + Prometheus + Grafana 监控体系，覆盖接口 QPS/AI 成功率/缓存命中率
  7. 匹配算法 JUnit 5 单元测试 12 用例 + Mockito Mock 测试 + Spring Boot Test 集成测试
  8. Docker Compose 一键部署（MySQL + Redis + App + Prometheus + Grafana）

## 三、高频面试题 & 满分回答模板

> 这些问题在阿里 P6/P7 面试中出现概率极高，提前准备好

### 题 1：这个项目你觉得最难的一个技术点是什么？

```
★ 满分回答结构：
1. 先说难点是什么（一句话）
2. 再说为什么难（技术挑战）
3. 最后说怎么解决的（具体方案 + 数据）

参考回答：
"最难的是匹配算法的设计。一开始我用编辑距离做全量匹配，2000 人时要跑 400 万次
两两比较，耗时超过 5 秒。后来我研究了搜索引擎的倒排索引思想，重新设计了一套
流程：先用倒排索引快速召回候选用户（只跟有共同标签的人比），再用 TF-IDF 加权
向量化，最后用余弦相似度精排。改造后耗时降到 0.89 秒，提升了 6 倍多。这个过程
让我真正理解了'索引加速检索'这个思想在不同场景下的应用。"
```

### 题 2：你的倒排索引是怎么实现的？和 ES 有什么区别？

```
参考回答：
"核心是一个 HashMap<String, Set<Long>>，标签 → 拥有该标签的用户 ID 集合。
优点是实现简单、零依赖、对少量标签场景非常高效。跟 ES 的区别在于：ES 有分词、
FST 词典树、跳表等复杂数据结构，适合海量文本全文检索；我的场景是少量标签的
精确匹配，HashMap 就够用了。如果以后用户量上百万，会考虑迁移到 ES。"

面试官心理：考察你是否盲目使用技术，有没有场景适配意识。
```

### 题 3：Redisson 分布式锁的原理？看门狗机制讲一下？

```
参考回答：
"Redisson 基于 Redis 的 SETNX + Lua 脚本实现分布式锁。它的看门狗机制解决了一个
关键问题：如果业务执行时间超过锁的过期时间怎么办？Redisson 会启动一个后台定时
任务，每 10 秒检查一次——如果锁还被当前线程持有，自动把过期时间续到 30 秒。
这样即使业务逻辑执行了 1 分钟，锁也不会提前释放。

另外，解锁时 Redisson 用 Lua 脚本保证原子性：先判断锁是不是自己的，是才释放。
避免了 A 线程误删 B 线程的锁。"

面试官心理：考察你是否真正理解，而不是只会调 API。
```

### 题 4：Spring Session Redis 是怎么做到无状态服务的？

```
参考回答：
"传统 Session 存在应用内存里，用户登录后如果下次请求路由到另一台机器，就拿不到
登录态了。Spring Session Redis 把 Session 数据存到 Redis 里，所有应用实例共享同
一个 Redis。它的原理是：请求进来时，Spring Session 的过滤器会拦截请求，从 Cookie
里拿到 Session ID，然后去 Redis 查对应的 Session 数据，反序列化后放进当前请求
上下文。对业务代码来说完全透明——还是 request.getSession().setAttribute()。
这样就实现了应用层无状态，可以随意扩缩容。"
```

### 题 5：如果你的 AI 推荐理由接口挂了，用户会看到什么？

```
参考回答：
"不会挂。我设计了 fallback 降级策略：try 块里调用 AI，catch 到异常后自动降级为
规则生成的推荐语。比如'你和XX都擅长Java，很适合一起协作'。这样即使AI服务不可用，
用户看到的仍然是合理的推荐理由，体验不会有断崖式下跌。

更进一步的话，我还会在 catch 里打一个监控埋点，连续失败 N 次就告警通知运维。"
```

### 题 6：你这个项目能抗多少 QPS？瓶颈在哪？

```
参考回答（诚实但有深度）：
"坦白说我没有做过完整的压力测试，目前是单机部署，估计匹配接口几十 QPS 没问题。
但我知道瓶颈会在哪里：

1. 数据库瓶颈：全量查用户做内存匹配，用户上万后 list() 就撑不住了
2. 匹配算法瓶颈：词汇表扩张导致向量维度膨胀，余弦计算变慢
3. AI 接口瓶颈：qwen-plus 的 QPS 限制

对应的优化方向：
1. 离线预计算 + Redis 缓存匹配结果
2. 稀疏向量替代稠密向量
3. AI 结果也缓存，相同标签组合的用户复用推荐理由

如果面试官追问，可以补充：自己虽然没做过压测，但用 JMH 对匹配算法做了
微基准测试，知道单次匹配在 2000 用户时的精确耗时（约 0.4ms/人）。"
```

### 题 7：你的缓存预热为什么用定时任务而不是启动时就预热？

```
参考回答：
"两种场景都要做。启动预热用 @PostConstruct 或 ApplicationRunner，定时预热用
@Scheduled。我的项目目前用的是定时预热（每天 23:58），原因是：

1. 推荐数据每天变化（新用户注册、修改标签），定时刷新保证数据时效性
2. 深夜执行避免和业务高峰期抢资源
3. 用 Redisson 分布式锁保证只有一个实例执行，避免多实例重复预热

启动预热也应该加——用 ApplicationRunner 在项目启动后立刻加载热门用户缓存，
这样刚部署完用户就有缓存命中。"
```

### 题 8：如果你要设计一个千万用户的匹配系统，会怎么设计？

```
参考回答（展示架构能力）：
"分四层设计：

1. 数据层：MySQL 做主存储，ES 做人名和标签的全文检索
2. 索引层：离线 Spark 任务每天凌晨计算用户向量（TF-IDF），存入向量数据库（Milvus）
3. 匹配层：实时匹配先用倒排索引粗筛（ES），再调 Milvus 做 ANN 近似向量检索 TopK
4. 推荐层：匹配结果缓存到 Redis，AI 推荐理由异步生成后写回

关键取舍：
- 牺牲一点匹配精度（ANN 近似 vs 精确余弦），换 2~3 个数量级的性能提升
- AI 推荐理由异步化，不阻塞匹配接口
- 热门用户（Top 20%）的结果预计算 + CDN 边缘缓存"
```

## 四、阿里面试官的"挖坑"问题（心理准备）

这些问题面试官不一定问，但如果问了你要知道怎么应对：

### 坑 1："你这个倒排索引跟 ES 比有什么优势？"

> 陷阱：不要吹自己比 ES 好。正确回答："没有优势，ES 功能强大得多。我的实现是针对少量标签精确匹配的场景特化的，零依赖、代码简单。场景变了该上 ES 得上 ES。"

### 坑 2："TF-IDF 有什么缺点？"

> 陷阱：不要只说优点。正确回答："TF-IDF 只考虑词频，不考虑词序和语义。比如'Java后端'和'后端Java'TF-IDF 认为是完全一样的，但实际上可能侧重点不同。更好的方案是 Word2Vec 或 BERT 做语义向量，但计算成本更高，需要权衡。"

### 坑 3："用了分布式锁，性能会不会受影响？"

> 陷阱：不要回避。正确回答："会有影响，但队伍加入是低频操作（用户不会每秒加入 100 个队伍），这点性能损失完全可以接受。如果是高频场景（如秒杀），需要用分段锁或 Redis 原子操作（DECR）减少锁粒度。"

### 坑 4："AI 推荐理由真的有用吗？用户会看吗？"

> 陷阱：考察产品思维。正确回答："坦诚说，我没有做 AB 测试验证。但理论上，可解释的推荐比'黑盒推荐'的信任度高。拼多多的'好友也买了'、抖音的'因为你关注了XX'都是这个道理。如果是我负责，我会做 AB 测试，对比有无推荐理由的匹配点击率和组队成功率。"

## 五、面试时的一句话亮点（必背）

以下每句话都可以在面试时自然地"不经意提到"，展示深度：

> 1. "我特意用 JMH 做了微基准测试，对比编辑距离和倒排索引的性能差异——因为在 JVM 上做性能测试，必须消除 JIT 预热的影响。"

> 2. "AI 调用我设计了降级策略 try-catch-fallback，因为第三方服务挂了不能影响我自己的核心功能。"

> 3. "标签树的三级转两级算法是一个实际踩过的坑——数据库设计了三层（技术→后端→Java），但前端 van-tree-select 只支持两层，需要我写算法层拍平。"

> 4. "分布式锁释放时我用 `isHeldByCurrentThread()` 判断，防止 A 线程释放了 B 线程的锁。"

> 5. "Spring Session Redis 让应用无状态，这是做负载均衡和水平扩展的前提——虽然当前是单机，但架构预留了这个能力。"
