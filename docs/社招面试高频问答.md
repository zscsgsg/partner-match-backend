## 一、缓存相关（必问，频率 ★★★★★）

### Q1：你的推荐缓存是怎么设计的？缓存穿透、击穿、雪崩分别怎么解决的？

**参考答案**：

**缓存结构**：Key = `zsc:user:recommend:{userId}:{page}:{size}`，Value = 序列化的 Page 对象。

**三大问题的解决方案**：

**1. 缓存穿透（查不存在的数据）**：
- 查询结果为空时，也缓存一个特殊标记 `EMPTY_PAGE`，TTL 设为 5 分钟
- 下次同样请求直接命中空值标记，返回空 Page，不会穿透到 DB
- 也可以用布隆过滤器（Redis Bitmap），但当前数据量不需要

**2. 缓存击穿（热点 key 过期瞬间大量请求）**：
- 缓存未命中时，用 Redisson 分布式锁 `zsc:cache:lock:recommend:{userId}` 保证只有一个线程重建缓存
- 其他线程等待 3 秒后重新读缓存（Double-check 模式）
- 获取锁失败的线程直接返回空页，不阻塞用户

**3. 缓存雪崩（大量 key 同时过期）**：
- TTL 不再是固定 120 分钟，而是 `120 + ThreadLocalRandom.nextInt(0, 30)` 分钟
- 每个用户的缓存过期时间错开 0~30 分钟，避免同一时刻大量 key 失效

```java
// 核心代码片段
if (records.isEmpty()) {
    redisTemplate.opsForValue().set(redisKey, EMPTY_CACHE_MARKER, 5, TimeUnit.MINUTES);
} else {
    long ttlMinutes = 120 + ThreadLocalRandom.current().nextInt(0, 30);
    redisTemplate.opsForValue().set(redisKey, userPage, ttlMinutes, TimeUnit.MINUTES);
}
```

---

### Q2：你的缓存 Double-check 是怎么做的？为什么要 double-check？

**参考答案**：

获取锁之后、查 DB 之前，再读一次缓存。因为可能存在这种情况：
1. 线程 A 和线程 B 同时发现缓存 miss
2. 线程 A 先拿到锁，查 DB 重建缓存后释放锁
3. 线程 B 拿到锁，如果不 double-check，会再查一次 DB（浪费资源）
4. Double-check 后发现缓存已有数据，直接返回

这和单例模式的双重检查锁是同一个思想。

---

### Q3：Redis 缓存和数据库一致性怎么保证？

**参考答案**：

当前项目推荐缓存的更新策略是 **Cache-Aside（旁路缓存）**：
- 读：先查缓存 → 命中直接返回 → 未命中查 DB 后写缓存
- 写：推荐结果没有写操作（只读场景），所以不存在一致性问题

如果未来有写操作（比如用户更新标签后推荐结果变化），策略是 **先更新 DB，再删除缓存**（而不是更新缓存），配合消息队列异步重试删除，保证最终一致性。

## 二、分布式锁相关（必问，频率 ★★★★★）

### Q4：你用 Redisson 分布式锁解决什么问题？为什么不用 synchronized？

**参考答案**：

**解决的问题**：
1. 队伍加入时的"超卖"——并发加入可能同时读到 count=4 都认为还能加
2. 缓存重建时防止多线程同时查 DB

**为什么不用 synchronized**：synchronized 只能保证单 JVM 内的互斥。如果部署多个实例（负载均衡），synchronized 管不住其他实例的线程。分布式锁基于 Redis，所有实例共享同一把锁。

---

### Q5：Redisson 的看门狗机制是什么？如果看门狗续锁失败了怎么办？

**参考答案**：

**看门狗（Watchdog）**：如果加锁时不指定 leaseTime，Redisson 默认锁 30 秒过期，然后启动一个后台线程（看门狗），每 10 秒检查一次——如果当前线程还持有锁，就把过期时间重新延长到 30 秒。

**续锁失败的情况**：
1. Redis 连接断了 → 锁会在 30 秒后自动过期释放，其他线程可以获取锁
2. 持有锁的线程 crash 了 → 看门狗也会停止，锁自动过期
3. 兜底方案：数据库层面加乐观锁（version 字段）或唯一索引，即使分布式锁失效，DB 也能兜底

---

### Q6：你的分布式锁在 Redis 主从切换时会不会有问题？

**参考答案**：

**会。** 单节点 Redisson 锁在主从切换时可能丢锁：
1. 客户端 A 在主节点拿到锁
2. 主节点宕机，锁还没同步到从节点
3. 从节点升级为新主，客户端 B 也拿到同一把锁
4. A 和 B 同时认为自己持有锁 → 互斥失效

**解决方案**：Redisson 提供 **RedLock（红锁）**，需要 N 个独立 Redis 节点（N 为奇数），必须在 N/2+1 个节点上加锁成功才算获取锁。或者用 ZooKeeper/Etcd 的 CP 一致性保证。

## 三、匹配算法相关（高频，频率 ★★★★☆）

### Q7：你的智能匹配算法具体怎么做的？

**参考答案**：

**三步：倒排索引召回 → TF-IDF 向量化 → 余弦相似度精排 + 多维度打分**

1. **倒排索引**：`Map<标签, Set<用户ID>>`，通过当前用户的标签快速召回有共同标签的候选人
2. **TF-IDF 加权**：`IDF(t) = log(总用户数/含标签t的用户数) + 1`，区分标签重要性
3. **余弦相似度**：`cos(u1, u2) = (u1·u2) / (|u1|×|u2|)`，对候选集精确排序
4. **多维度打分**：标签相似度 65% + 行为相似度 20% + 互补性 10% + 协作评分 5%

**压测数据**：2000 用户全量匹配，旧算法 5509ms → 新算法 894ms，提升 6.16 倍。

---

### Q8：你的用户画像系统怎么做的？怎么反馈到匹配算法的？

**参考答案**：

**画像数据来源**：从 `team` 表和 `user_team` 表统计每个用户的：
- 创建队伍数、加入队伍数
- 平均组队时长（天）
- 偏好标签 Top5（统计自己 + 队友的标签出现频率）
- 协作评分（公式：`min(5.0, 1.0 + 组队次数×0.3 + 平均时长×0.05)`）

**反馈到算法**：
- **行为相似度**：用真实的 `totalTeamsCreated` 和 `totalTeamsJoined` 替代之前的硬编码 `(0,0,0,0)`
- **协作评分维度**：评分高的用户在匹配时加分（归一化到 0~1，权重 5%）
- 形成数据闭环：用户组队行为 → 更新画像 → 影响匹配权重 → 推荐更好的队友

### Q9：你的倒排索引和 Elasticsearch 的倒排索引有什么区别？什么时候该上 ES？

**参考答案**：

| 维度 | 我的实现 | Elasticsearch |
|------|---------|--------------|
| 场景 | 标签精确匹配 | 海量文本全文检索 |
| 数据结构 | HashMap | FST + Posting List + Skip List |
| 数据规模 | 内存级（千级标签） | TB 级 |
| 分词 | 不需要（标签是离散的） | 需要（中文分词、同义词） |

**什么时候上 ES**：标签数上千、用户百万级、需要模糊搜索（标签联想）时。当前 40 用户、20 个标签，上 ES 是过度设计。

## 四、接口限流相关（高频，频率 ★★★★☆）

### Q10：你的接口限流怎么做的？为什么选 Guava RateLimiter？

**参考答案**：

**实现方式**：自定义 `@RateLimit` 注解 + AOP 切面拦截。

```java
@GetMapping("/match/smart")
@RateLimit(qps = 5, fallbackMsg = "智能匹配请求过于频繁，请稍后再试")
```

AOP 切面中用 `ConcurrentHashMap` 为每个方法维护一个 `RateLimiter` 实例（懒加载），通过 `tryAcquire()` 尝试获取令牌。

**为什么选 Guava RateLimiter**：
- **令牌桶算法**：允许一定程度的突发流量（桶里有积累令牌时）
- **轻量级**：单机限流，不需要 Redis 等外部依赖
- **简单**：一行 `RateLimiter.create(5)` 就搞定

**和 Sentinel 的区别**：Sentinel 更强大（滑动窗口、熔断降级、集群限流），但更重。当前场景 Guava 够用。

---

### Q11：限流和熔断有什么区别？你的 AI 接口有做熔断吗？

**参考答案**：

| 维度 | 限流 | 熔断 |
|------|------|------|
| 目的 | 控制请求速率 | 保护下游服务 |
| 触发条件 | QPS 超过阈值 | 错误率超过阈值 |
| 行为 | 拒绝多余请求 | 停止调用下游，直接走 fallback |
| 恢复 | 持续放行 | 半开探测，成功后恢复 |

当前 AI 接口做了限流 + fallback 降级（AI 调用失败走规则理由），但没有做正式的熔断。如果要加，可以用 Sentinel 或 Resilience4j：连续失败 5 次自动熔断，60 秒后半开探测。

## 五、WebSocket 聊天室（高频，频率 ★★★★☆）

### Q12：你的 WebSocket 聊天室怎么做的？消息怎么持久化的？

**参考答案**：

**架构设计**：
- 端点：`@ServerEndpoint("/ws/team/{teamId}/{userId}/{userName}")`
- 房间管理：`ConcurrentHashMap<Long, CopyOnWriteArraySet<Session>>`，key = teamId
- 消息流：客户端发送 → 服务端持久化到 MySQL → 广播给同房间所有 Session

**消息持久化**：每条消息保存到 `chat_message` 表（teamId, senderId, senderName, content, createTime），支持历史消息分页查询 `GET /team/{teamId}/messages`。

**关键细节**：
- 用 `CopyOnWriteArraySet` 管理 Session，避免并发修改异常
- 发送消息用 `session.getBasicRemote().sendText()`，加了 isOpen() 判断防止向已关闭连接发送
- `@ServerEndpoint` 每次连接都 new 实例，所以 Spring Bean 通过 static + setter 注入

---

### Q13：WebSocket 连接断了怎么办？在线人数怎么统计？

**参考答案**：

**断线处理**：`@OnClose` 回调中从房间 Map 移除 Session，从 `SESSION_ROOM` 映射中也清除，并广播"XX 离开了聊天室"。

**在线统计**：用 `volatile int onlineCount` 原子计数，`onOpen` 时 +1，`onClose` 时 -1。

**前端断线重连**（如果要加的话）：WebSocket `onclose` 事件中启动定时器，每隔 5 秒尝试重连，最多重试 3 次。

---

### Q14：如果同一个用户开了两个浏览器标签页，你的聊天室会怎样？

**参考答案**：

会建立两个 WebSocket 连接，两个 Session 都在同一个房间里。发消息时两个标签页都能收到——这是正确行为（多端同步）。

但有一个小问题：`onlineCount` 会 +2 而不是 +1。如果要精确统计独立用户数，需要用 `Map<Long, Set<Session>>` 按 userId 去重。

## 六、监控体系相关（中频，频率 ★★★☆☆）

### Q15：你的监控体系怎么搭建的？Prometheus 和 Grafana 各自的作用是什么？

**参考答案**：

**架构**：应用（Micrometer）→ Prometheus（采集+存储）→ Grafana（可视化+告警）

**各组件职责**：
- **Micrometer**：Java 指标门面库，类似 SLF4J 但用于 metrics。通过 `Counter`、`Timer`、`Gauge` 注册自定义指标
- **Prometheus**：定时拉取 `/actuator/prometheus` 端点，存储时间序列数据，支持 PromQL 查询
- **Grafana**：连接 Prometheus 数据源，建 Dashboard 面板，配置告警规则

**自定义业务指标**：
| 指标名 | 类型 | 说明 |
|--------|------|------|
| `match.request.count` | Counter | 匹配请求总次数 |
| `match.request.duration` | Timer | 匹配接口耗时 |
| `ai.call.success` / `ai.call.fail` | Counter | AI 调用成功/失败数 |
| `cache.hit` / `cache.miss` | Counter | 缓存命中/未命中数 |

**面试加分**："我能告诉你 AI 调用成功率是 98%，匹配接口 P99 耗时 200ms，缓存命中率 85%"——这比"大概挺快的"强一百倍。

## 七、安全与配置相关（中频，频率 ★★★☆☆）

### Q16：你的 API Key 和密码怎么管理的？

**参考答案**：

改造前是明文写在 `application.yml` 里，这是严重的安全隐患。

改造后：
- `application.yml` 所有敏感值用 `${ENV_VAR}` 占位符，如 `${DB_PASSWORD}`、`${AI_API_KEY}`
- 新建 `application-example.yml` 模板（含说明，不含真实值），提交到 Git
- `.gitignore` 排除 `application.yml`
- 部署时通过环境变量或 `.env` 文件注入真实值

**生产环境进一步**：用 Nacos/Apollo 配置中心管理，支持动态刷新和权限控制。

## 八、日志与排查（中频，频率 ★★★☆☆）

### Q17：线上出了 bug 你怎么排查？

**参考答案**：

**排查三板斧**：日志 + 监控 + 链路追踪

1. **日志**：
   - `logback-spring.xml` 配置按天滚动，全量日志 + 错误日志分离
   - 关键操作都有 `log.info`：`[用户注册]`、`[加入队伍]`、`[智能匹配]`（含耗时）
   - 全局异常处理器 `log.error` 输出完整异常栈

2. **监控**：
   - Prometheus + Grafana 面板看接口 QPS、AI 成功率、缓存命中率
   - 告警：AI 连续失败 5 次自动通知

3. **排查流程**：
   - 先看 Grafana 面板定位是哪个接口异常
   - 去 Kibana/日志文件搜关键词（userId、traceId）
   - 看异常栈定位代码行
   - 修复后跑单元测试验证

## 十、Docker 部署（中频，频率 ★★☆☆☆）

### Q19：你的项目怎么部署的？Docker Compose 里有哪些服务？

**参考答案**：

**Dockerfile 多阶段构建**：
- 阶段 1（builder）：Maven 编译打包
- 阶段 2（runtime）：仅 JRE Alpine 镜像，最终镜像约 200MB

**docker-compose.yml 一键启动 6 个服务**：

| 服务 | 镜像 | 端口 |
|------|------|------|
| MySQL 8.0 | mysql:8.0 | 3306 |
| Redis 7 | redis:7-alpine | 6379 |
| 应用 | 自构建 | 8083 |
| Prometheus | prom/prometheus | 9090 |
| Grafana | grafana/grafana | 3000 |
| Nginx（前端） | nginx:alpine | 9999 |

MySQL 和 Redis 配了 healthcheck，应用 depends_on 等待健康检查通过后才启动，避免启动时连不上数据库。
