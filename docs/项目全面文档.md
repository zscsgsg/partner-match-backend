## 一、项目概述

**伙伴匹配系统**是一个面向技术爱好者的智能组队平台。用户可以通过标签体系描述自己的技能，系统基于 TF-IDF 加权 + 倒排索引召回 + 余弦相似度精排的算法，为用户推荐最佳匹配伙伴，并通过 AI（通义千问）生成自然语言推荐理由。此外还提供队伍内实时聊天、用户画像分析、接口监控、缓存防护、接口限流等生产级功能。

### 核心亮点

| 亮点               | 说明                                                         |
| ------------------ | ------------------------------------------------------------ |
| **智能匹配算法**   | 自研 TF-IDF + 倒排索引 + 余弦相似度，全量匹配场景性能提升 6.16x |
| **用户画像系统**   | 组队行为统计 + 协作评分 + 偏好标签，反馈到匹配权重形成数据闭环 |
| **AI 推荐解释**    | Spring AI Alibaba + qwen-plus生成推荐理由，含 fallback 降级 + 限流 |
| **缓存防护**       | 穿透防护（空值缓存）+ 击穿防护（Redisson 互斥锁）+ 雪崩防护（TTL 随机化） |
| **WebSocket 聊天** | 队伍内实时聊天室，消息持久化 + 历史消息分页 + 房间管理       |
| **监控体系**       | Micrometer + Prometheus + Grafana，覆盖 QPS/AI 成功率/缓存命中率 |
| **接口限流**       | Guava RateLimiter + 自定义 @RateLimit 注解 + AOP 拦截        |
| **事件驱动解耦**   | Spring ApplicationEvent 机制，队伍变更自动触发画像重算 + 缓存失效 |
| **自动化测试**     | JUnit 5 + Mockito + Spring Boot Test，匹配算法 12 个单元测试用例 |
| **Docker 部署**    | 多阶段构建 + docker-compose 一键启动 6 个服务                |

### JDK 21 特性使用说明

项目选择 JDK 21（而非 JDK 17）的核心原因是利用其新特性提升系统性能与代码质量：

#### 已使用的 JDK 21 特性

| 特性 | 引入版本 | 使用位置 | 作用 |
| ---- | -------- | -------- | ---- |
| **虚拟线程（Virtual Threads）** | JDK 21 GA | `MatchExplainService.fillExplanations()` | 并行调用通义千问 AI 接口，内存开销从每线程 ~1MB 降至几 KB，10 条匹配结果并行生成推荐理由总耗时 ≤ 3s |
| **Stream.toList()** | JDK 16 | `UserServiceImpl`、`TeamController` 等多处 | 替代 `.collect(Collectors.toList())`，返回不可变列表，代码更简洁 |

#### 虚拟线程使用详情

```java
// MatchExplainService.java
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (MatchResult result : results) {
        CompletableFuture.runAsync(() -> {
            result.explanation = generateExplanation(...);
        }, executor)
        .orTimeout(3, TimeUnit.SECONDS)   // 单条 3s 超时
        .exceptionally(ex -> {            // 超时降级为规则理由
            result.explanation = fallbackExplanation(...);
            return null;
        });
    }
    CompletableFuture.allOf(futures).orTimeout(6, TimeUnit.SECONDS).join();
}
```

**为什么选虚拟线程而不是传统线程池？**
- AI 接口调用是典型 I/O 密集型任务，传统线程池每个线程占用 ~1MB 栈内存
- 10 条匹配结果并行 = 10 个 OS 线程 = 10MB 内存浪费
- 虚拟线程是用户态线程，由 JVM 调度，内存仅几 KB，可轻松创建数万个并发任务
- Spring Boot 3.5 原生支持 JDK 21，虚拟线程与 `CompletableFuture` 无缝配合

### 5.4 匹配算法体系

系统内建**两套匹配算法**，分别用于不同场景：

#### 算法一：编辑距离匹配（matchUsers）

| 项目     | 说明                                           |
| -------- | ---------------------------------------------- |
| API      | `GET /user/match`                              |
| 前端     | ❌ 未接入                                       |
| 算法     | 编辑距离（Levenshtein Distance）比较标签列表    |
| 复杂度   | O(n² × k²)，n=用户数，k=人均标签数             |
| 适用规模 | < 500 用户                                      |

#### 算法二：TF-IDF + 倒排索引智能匹配（smartMatchUsers）

| 项目     | 说明                                                        |
| -------- | ----------------------------------------------------------- |
| API      | `GET /user/match/smart`（每秒限流 5 次）                    |
| 前端     | ✅ IndexPage → AI 智能匹配开关                               |
| 算法     | TF-IDF 加权 → 倒排索引召回 → 余弦相似度精排 → 多维度打分    |
| 复杂度   | O(N×T + C×V)，C=候选集，V=词汇表大小                         |
| 缓存     | ✅ Redis 三层防护（穿透/击穿/雪崩），TTL 10~20 分钟          |

#### 智能匹配算法流程

```
1. 构建全局词汇表
   遍历所有用户标签 → 去重 → 分配维度索引

2. 计算 IDF 权重
   IDF(t) = log(总用户数 / 包含标签t的用户数) + 1

3. 构建倒排索引
   Map<标签, Set<用户ID>>

4. 倒排查召候选集（性能关键！）
   通过当前用户的标签查倒排索引 → 取并集 → 排除自己
   → 候选集从 O(N) 降到 O(C)，C << N

5. TF-IDF 向量化
   用户标签 → TF归一化 → × IDF → 稀疏向量

6. 余弦相似度精排
   cos(u1, u2) = (u1·u2) / (|u1|×|u2|)

7. 多维度综合打分（画像权重）
   totalScore = 标签相似度×65% + 行为相似度×20% + 互补性×10% + 协作评分×5%
```

#### 性能测试结果

| 场景                 | 旧算法（编辑距离） | 新算法（倒排索引） | 提升      |
| -------------------- | ------------------ | ------------------ | --------- |
| 500 用户 × 全量匹配  | 323.6 ms           | 59.9 ms            | **5.40x** |
| 1000 用户 × 全量匹配 | 1317.7 ms          | 218.9 ms           | **6.02x** |
| 2000 用户 × 全量匹配 | 5509.9 ms          | 894.7 ms           | **6.16x** |

> 测试环境：500 标签池 / 每用户 3~8 标签 / 全量批量匹配

#### 100 万用户性能预估

> ⚠️ 本轮已优化：画像查询从 N+1（100 万次 SQL → 17 分钟）改为 1 次批量查询（~2 秒）

| 阶段                  | 复杂度      | 1万用户 | 100万用户（优化后） | 瓶颈                  |
| --------------------- | ----------- | ------- | ------------------- | --------------------- |
| ① 查询所有用户（DB）   | O(N)        | ~50ms   | ~1s                 | DB 全表扫描           |
| ② 批量查画像（1次SQL） | O(1)        | ~30ms   | ~2s                 | DB IN 子句长度        |
| ③ 构建词汇表 + IDF     | O(N×T)      | ~30ms   | ~3s                 | 内存 / GC 压力        |
| ④ 构建倒排索引         | O(N×T)      | ~20ms   | ~2s                 | 同上                  |
| ⑤ 倒排查召候选集       | O(T)        | 瞬间    | 瞬间                | -                     |
| ⑥ 余弦相似度精排       | O(C×V)      | ~100ms  | 取决于标签分布      | **最大瓶颈**          |
| ⑦ AI 解释（10条并行）  | O(1×3s)     | ~3s     | ~3s                 | AI API 延迟           |

**关键瓶颈分析**：候选集 C 取决于标签重叠度
- 标签分散（如"Spring Security"只有 500 人标记）→ C ≈ 5,000 → ⑥ ≤ 200ms ✅ 总耗时 ~10s
- 热门标签集中（如"Java"被 50 万人标记）→ C ≈ 500,000 → ⑥ 30~60 秒 ❌

**✅ 本轮优化：2 项**
- 画像查询 N+1 → 批量查询：100万次SQL → 1次，17分钟 → 2秒
- Redis 缓存：首次计算后缓存 10~20 分钟，后续命中 ≤ 10ms

**🔮 后续优化方向**：
- 候选集上限截断（max 5000）
- 预计算用户向量存 Redis（免去每轮 TF-IDF 计算）
- 离线 Spark/Flink 预计算匹配结果，在线只读

## 5.5 事件驱动机制（Spring ApplicationEvent）

队伍变更操作（创建/加入/退出/删除）会触发多个后续动作（画像重算、缓存失效）。为避免在 `TeamServiceImpl` 中硬编码这些逻辑，项目采用 **Spring 事件驱动机制** 实现业务解耦。

#### 架构设计

```
TeamServiceImpl ──发布──▶ TeamEvent ──监听──▶ TeamEventListener
                         (JOIN/QUIT/           ├─ 画像重算（同步）
                          CREATE/DELETE)        └─ 缓存失效（异步 @Async）
```

#### 核心组件

| 组件 | 文件 | 职责 |
| ---- | ---- | ---- |
| `TeamEvent` | `event/TeamEvent.java` | 事件载体，包含 userId、teamId、eventType（CREATE/JOIN/QUIT/DELETE） |
| `TeamEventListener` | `event/TeamEventListener.java` | 监听事件，触发画像重算 + 缓存失效 |
| `ApplicationEventPublisher` | 注入 TeamServiceImpl | 发布事件的统一入口 |

#### 事件触发场景

| 操作 | 事件类型 | 触发时机 | 后续动作 |
| ---- | -------- | -------- | -------- |
| `addTeam` 创建队伍 | CREATE | 队伍 + 关联记录插入成功后 | 重算创建者画像 + 清缓存 |
| `joinTeam` 加入队伍 | JOIN | user_team 记录插入成功后 | 重算加入者画像 + 清缓存 |
| `quitTeam` 退出队伍 | QUIT | 用户关联记录删除后 / 队伍解散时 | 重算退出者画像 + 清缓存 |
| `deleteTeam` 删除队伍 | DELETE | 队伍删除成功后，为**每个成员**分别发布 | 重算所有队员画像 + 清缓存 |

#### 关键实现

```java
// 发布事件（TeamServiceImpl 中只需一行）
applicationEventPublisher.publishEvent(
    new TeamEvent(this, loginUser.getId(), teamId, TeamEvent.EventType.JOIN));

// 监听器 1：同步画像重算
@EventListener
public void onTeamChangeRecalculateProfile(TeamEvent event) {
    userProfileService.calculateProfile(event.getUserId());
}

// 监听器 2：异步缓存失效（@Async 不阻塞主业务）
@Async
@EventListener
public void onTeamChangeInvalidateCache(TeamEvent event) {
    // 清除推荐缓存 + 智能匹配缓存
    stringRedisTemplate.delete(keys);
}
```

#### 设计优势

- **解耦**：TeamServiceImpl 不依赖 UserProfileService 和 RedisTemplate
- **开闭原则**：新增后续动作（如站内通知）只需新建监听器，核心代码零修改
- **异步不阻塞**：缓存失效用 `@Async` 异步执行，不影响主业务响应时间
- **容错隔离**：监听器内 try-catch，某个监听器失败不影响其他监听器

### 5.6 AI 推荐理由（MatchExplainService）

基于 **Spring AI Alibaba** + **qwen-plus** 为匹配结果生成自然语言推荐理由。

#### 实现要点

1. **Prompt 工程**：构造用户标签、简介、共同点等信息拼接 prompt
2. **并行调用**：10 条匹配结果通过虚拟线程并行调用 AI，总耗时 ≤ 3 秒
3. **超时兜底**：单条 AI 调用 3 秒超时自动降级为规则生成理由
4. **批量超时**：整体等待 ≤ 6 秒，超时后剩余未完成的结果使用规则理由

```java
// 并行 + 超时 + 降级
CompletableFuture.runAsync(() -> {
    result.explanation = generateExplanation(...);
}, executor)
.orTimeout(3, TimeUnit.SECONDS)         // 单条 3s 超时
.exceptionally(ex -> {
    result.explanation = fallbackExplanation(...);  // 降级为规则理由
    return null;
});
```

#### 降级策略

```java
// AI 失败时的回退策略
private String fallbackExplanation(String nameA, String nameB, String commonTags) {
    if (!"无明显共同标签".equals(commonTags)) {
        return String.format("你和%s都擅长%s，很适合一起协作。", nameB, commonTags);
    }
    return String.format("%s的技能方向与你有差异，互补组队可以碰撞出不一样的火花。", nameB);
}
```

### 5.7 Redis 缓存

#### 缓存策略

| 场景       | Key 格式                           | 过期时间     | 防护策略                                |
| ---------- | ---------------------------------- | ------------ | --------------------------------------- |
| 推荐用户   | `zsc:user:recommend:{userId}:...`  | 2 小时       | 穿透（空值 5min）+ 击穿（Redisson 锁）+ 雪崩（TTL 随机 ±30min） |
| 智能匹配   | `zsc:user:smartMatch:{userId}:{n}` | 10~20 分钟   | 穿透（空值 3min）+ 击穿（Redisson 锁）+ 雪崩（TTL 随机 ±10min） |
| 用户登录态 | `userLoginState`                   | 24 小时      | Spring Session Redis 管理               |

#### 缓存防护实现（以智能匹配为例）

```java
// 1. 读缓存 → 2. 互斥锁 Double-Check → 3. 计算 → 4. 缓存（TTL 随机）
String redisKey = String.format("zsc:user:smartMatch:%s:%s", userId, num);
if (cached != null) return cached;         // 缓存命中

RLock lock = redissonClient.getLock(lockKey);
if (lock.tryLock(3, 10, SECONDS)) {
    // Double-Check → 执行匹配 → 缓存（随机 TTL 防雪崩）
    redisTemplate.opsForValue().set(redisKey, voList, 10+random(0,11), MINUTES);
}
// 空结果也缓存 3 分钟（防穿透）
if (voList.isEmpty()) redisTemplate.opsForValue().set(redisKey, "EMPTY", 3, MINUTES);
```

## 八、关键技术决策

### 8.1 为什么不用 Elasticsearch？

当前数据量（< 1000 用户）使用内存匹配 + 倒排索引完全够用，引入 ES 增加运维复杂度。未来用户增长后可平滑迁移，倒排索引思想一致。

### 8.2 为什么用 MD5 而不是 Bcrypt？

MD5 + 盐值对当前规模已足够，且实现简洁。生产环境建议 Bcrypt/Argon2。

### 8.3 标签为什么存在 MySQL JSON 字段而不是关联表？

每个用户 2~8 个标签，JSON 字符串查询性能足够且无需 join。倒排索引在内存中构建，不依赖 DB 关联查询。

### 8.4 智能匹配为什么要有缓存？

首次计算需 3~8 秒（含 AI 调用），100 万用户时候选集可能达 50 万。Redis 缓存后命中仅需 ~10ms，且配合互斥锁防止缓存击穿引发的重复计算风暴。

### 8.5 AI 解释为什么用并行而不是串行？

10 条结果串行调 AI 需 10~30 秒，改为虚拟线程并行 + 单条 3s 超时兜底后，最长 6 秒全部返回（含降级理由），用户体验从"超时报错"提升为"秒级出结果"。

每个场景包含预热轮次（消除 JIT 影响）+ 正式测试轮次。通过 `run_bench.ps1` 一键启动：

```powershell
.\run_bench.ps1
```
