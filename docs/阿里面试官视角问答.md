## 一、匹配算法相关

### Q1：你说你设计了智能匹配算法，具体怎么做的一步步讲给我听？

**参考答案**：

整个算法分为 **三步：倒排索引召回 → TF-IDF 向量化 → 余弦相似度精排**。

**第一步：构建倒排索引。** 类似搜索引擎的做法，我把所有用户的标签扫描一遍，建立一个 `Map<标签, Set<用户ID>>` 的映射。比如"Java"这个标签被 100 个人拥有，倒排索引就能快速告诉我这 100 个人是谁。

**第二步：TF-IDF 加权向量化。** 不是所有标签都同等重要——如果 90% 的人都标了"后端"，那这个标签区分度就很低。我用 IDF（逆文档频率）给标签加权：`IDF = log(总用户数/拥有该标签的用户数) + 1`。然后把每个用户的标签列表转成一个加权向量，维度 = 全局标签种类数。比如用户有"Java"、"Go"、"Rust"，那就只有这三个维度有非零值（TF×IDF），其他全是 0。

**第三步：余弦相似度精排。** 通过当前用户的标签去倒排索引里查，只召回跟它有共同标签的候选用户（而不是全量 2000 人都算一遍）。然后对每个候选人做余弦相似度计算，排出 TopN。

**额外加分**：我做了多维度打分，标签相似度权重 65%，行为相似度 20%，互补性 10%，协作评分 5%。这样既有"志同道合"又有"优势互补"的匹配效果，协作评分高的用户在匹配中也会获得一定加分。

**压测数据**：2000 用户全量匹配，旧算法 O(N²) 耗时 5509ms，新算法 894ms，提升 **6.16 倍**。而且用户越多优势越大。

### Q2：为什么不直接用编辑距离，要搞 TF-IDF + 倒排索引？

**参考答案**：

编辑距离有 **三个致命问题**：

1. **语义丢失**："Spring Boot" 和 "Spring Cloud" 编辑距离很大（因为字符串不同），但语义上它们是相似的。TF-IDF + 余弦可以捕捉这种关联性，因为拥有"Spring Boot"的人大概率也标了其他 Spring 生态标签。

2. **无法区分标签重要性**：编辑距离把所有标签一视同仁。但"Java"出现频率高，区分度低，而"Rust"出现频率低，区分度高。TF-IDF 天然解决了这个权重问题。

3. **全量匹配场景 O(N²)**：如果是给每个用户找匹配（批量推荐），编辑距离必须做 O(N²) 次两两比较。我的倒排索引一次建完后，每个用户只跟有共同标签的人比较——2000 用户场景下从 400 万对降到几十万对。

### Q3：你的倒排索引和 Elasticsearch 的倒排索引有什么区别？

**参考答案**：

思想是一样的——"词 → 文档列表"的反向映射。Elasticsearch 的倒排索引更复杂，有分词、词典树（FST）、跳表（Skip List）等优化。

我的实现是**场景特化的轻量版本**：

- ES 针对海量文本全文检索，我针对少量标签精确匹配
- ES 的数据结构（terms dictionary、posting list）对 TB 级数据做了极致优化
- 我的实现只需要一次 HashMap 构建，代码不到 30 行，零外部依赖

**什么时候该上 ES？** 当标签数达到数千个、用户数上百万时，内存 HashMap 会撑不住，而且需要模糊匹配（标签联想）时，ES 就派上用场了。但我这个项目 40 个用户、20 个标签，上 ES 是过度设计。

---

### Q4：你的算法时间复杂度是多少？空间复杂度呢？

**参考答案**：

**单次查询**：

- 建索引：O(N × T)，N=用户数，T=每人平均标签数
- 召回 + 精排：O(C × V)，C=候选人数，V=词汇表大小
- 总：O(N × T + C × V)

**全量匹配（N 个用户都查一遍）**：

- 旧算法（编辑距离）：O(N² × T²)
- 新算法（建一次索引 + N 次查询）：O(N × T + N × C_avg × V) ≈ O(N² × T² / V)

在稀疏场景下（V 大、T 小），C_avg = T²N/V 远小于 N，所以实际比 O(N²) 快很多。

**空间复杂度**：O(N × T) 存储倒排索引 + O(N × V) 存储向量（实际是稀疏的，可优化）。

---

### Q5：如果用户有 10 万个，你的算法还撑得住吗？

**参考答案**：

**瓶颈分析**：

1. 词汇表大小 V 随用户增长而增长，向量维度变大，余弦计算变慢
2. 倒排索引的 posting list 变长，候选集变大

**优化方案**：

1. **稀疏向量**：当前是 `double[V]` 稠密数组，用户只有 3~5 个标签却要遍历 500 维。改成 `Map<Integer, Double>` 稀疏表示，余弦计算只迭代非零维，复杂度从 O(V) 降到 O(T)
2. **分批处理**：把 10 万用户按活跃度分片，先匹配活跃用户
3. **离线预计算**：定时任务（如每天凌晨）预计算所有用户的 TopK 匹配，存入 Redis
4. **换 ES**：上 Elasticsearch 的 dense_vector + cosineSimilarity 查询，秒级返回
5. **ANN 近似搜索**：Faiss / Milvus 做向量近似最近邻，牺牲一点精度换几个数量级的性能提升

## 二、Redis / 分布式相关

### Q6：你用 Redisson 分布式锁解决什么问题？怎么实现的？如果锁失效了怎么办？

**参考答案**：

**解决的问题**：队伍加入时的"超卖"——队伍最多 5 人，并发加入时可能同时读到 `count=4` 然后都认为还能加，导致超员。

**实现方式**：

```java
RLock lock = redissonClient.getLock("sc:user:team:lock");
if (lock.tryLock(3, 10, TimeUnit.SECONDS)) {
    // 查人数 → 判断满员 → 插入记录
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```

**Redisson 的看门狗机制**：默认锁 30 秒过期，但只要持有锁的线程还活着，看门狗每 10 秒自动续期（延长到 30 秒），防止业务执行时间超过锁过期时间。

**如果锁失效了怎么办？**

1. **主从切换导致锁丢失**：Redisson 提供 `RedissonRedLock`（红锁），需要多个独立的 Redis 节点都加锁成功才算获取锁。当前项目是单机 Redis，所以没配，但如果要上生产必须考虑
2. **兜底方案**：数据库层面加唯一索引或乐观锁（version 字段），即使分布式锁失效，DB 也能兜底

### Q7：你的推荐缓存怎么设计的？缓存穿透了怎么办？

**参考答案**：

**缓存结构**：

- Key：`zsc:user:recommend:{userId}`
- Value：序列化的分页对象（Page<User>）
- TTL：2 小时

**缓存预热**：每天 23:58 定时任务，用 Redisson 锁保证单机执行，为 1~10 号白名单用户预加载推荐缓存。这样第二天早上这些用户直接命中缓存，避免冷启动。

**缓存穿透问题**：如果查一个不存在的 userId，缓存里没有，每次都穿透到 DB。解决方案：

- **布隆过滤器**：用 Redis Bitmap 存储所有存在的 userId，查询前先判是否存在
- **缓存空值**：把 `userId=999` 的结果也缓存（如缓存一个空 Page），TTL 设置短一点（5 分钟）
- 当前项目还没做，因为用户量小，但面试时主动提出来说明考虑到了

---

### Q8：Spring Session Redis 和直接用 Redis 存 Session 有什么区别？

**参考答案**：

**本质是一回事**——Spring Session Redis 就是把 HTTP Session 的数据存到 Redis 而不是应用内存里。

**区别在于带来的好处**：

1. **无状态服务**：多个后端实例共享同一个 Redis，用户请求路由到任何一台机器都能拿到登录态。这是做负载均衡的基础
2. **会话不丢**：应用重启不会丢 Session，用户体验好
3. **自动管理**：Spring Session 自动处理序列化/反序列化、过期清理，开发者不需要手动管理

**实际配置**：`spring.session.store-type=redis`，配好 Redis 连接信息，代码里还是 `request.getSession().setAttribute()`，完全无感切换。

## 三、AI 相关

### Q9：你的 AI 推荐理由怎么做的？为什么选 qwen-plus？

**参考答案**：

**技术选型**：用 Spring AI Alibaba 封装了对通义千问的调用，一行 `chatModel.call(prompt)` 就能拿到 AI 回复。它抽象了不同的 AI 厂商，换模型只需要改配置。

**为什么选 qwen-plus**：

1. **性能均衡**：qwen-plus 在能力和成本之间取得良好平衡，适合推荐理由生成这类需要一定语言理解能力又高频调用的场景
2. **Spring AI Alibaba 原生支持**：阿里出品，和 Spring Boot 集成度最高
3. **中文友好**：推荐理由要用中文输出，qwen 的中文能力比 Llama 等开源模型好得多

**容错设计**：

```java
try {
    return chatModel.call(prompt);
} catch (Exception e) {
    return fallbackExplanation(...); // AI 挂了自动降级
}
```

AI 不是必选项，挂了就降级到规则生成的推荐语，比如"你和 XX 都擅长 Java，很适合一起协作"。对用户来说体验不会断崖式下跌。

---

### Q10：如果 AI 返回的内容不合适（比如乱码、骂人），你怎么处理？

**参考答案**：

这是一个很好的安全/质量兜底问题，目前项目还没做，但思路是：

1. **输出长度限制**：prompt 里要求"不超过 80 字"，model 的 `max_tokens` 也可以配置
2. **敏感词过滤**：拿到 AI 返回后过一遍敏感词库，命中就降级为规则模板
3. **内容正则校验**：要求输出纯中文，检测到非预期字符就降级
4. **人工审核**：后台可以做一个推荐理由审核页面（长期方案）
5. **A/B 测试**：部分用户展示 AI 理由，部分展示规则理由，对比点击率/匹配转化率

## 四、数据库 / 架构设计

### Q11：你的标签为什么存在 user 表的一个 JSON 字段里，而不是建一个 user_tag 关联表？

**参考答案**：

**当前方案（JSON 字段）**：

- 优点：查询用户时一次 SQL 拿到所有标签，不用 join；标签少（2~8 个），JSON 解析开销极小
- 缺点：无法按标签直接 SQL 查询（要 LIKE 或全量查出来后内存过滤）

**关联表方案（user_tag 表）**：

- 优点：可以 `SELECT * FROM user WHERE id IN (SELECT userId FROM user_tag WHERE tagName='Java')`，SQL 层面精确查询
- 缺点：每个用户多 2~8 行数据，查用户基本信息需要 join

**我选 JSON 的原因**：

1. 当前数据量小（40 用户），内存遍历完全够
2. 匹配算法的核心在内存中的倒排索引，不依赖 DB 查询标签
3. 减少表数量，降低维护成本

**什么时候换关联表？** 当用户量上万，需要支持按标签精确筛选且不能全量加载到内存时。

---

### Q12：项目里 MyBatis-Plus 和 MyBatis 的区别？为什么用 MyBatis-Plus？

**参考答案**：

MyBatis 是半自动的 ORM 框架，需要手写 SQL。MyBatis-Plus 是在 MyBatis 之上做了增强：

1. **通用 CRUD**：`baseMapper.selectPage()` 一行搞定分页，不用写 XML
2. **条件构造器**：`LambdaQueryWrapper` 用 Lambda 表达式写查询条件，编译期就能检查字段名是否正确
3. **逻辑删除**：`@TableLogic` 注解，删数据自动变成 `UPDATE SET is_deleted=1`
4. **分页插件**：自动拦截 SQL 拼接 `LIMIT`

实际使用中，简单查询用 MyBatis-Plus 的 API，复杂查询（多表 join）仍然写 XML。两者不冲突。

### Q13：你说你用了 @Transactional，在这个项目里有什么坑吗？

**参考答案**：

项目中队伍解散时用了 `@Transactional`：

```java
@Transactional
public boolean deleteTeam(Long id, User loginUser) {
    this.removeById(id);                      // 删 team 表
    userTeamService.remove(...);              // 删 user_team 关联表
}
```

**两个关键点**：

1. **Spring 事务默认只回滚 RuntimeException**，如果方法内部 try-catch 了异常，事务不会回滚
2. **分布式锁 + 事务的顺序**：应该在事务外获取锁、事务内执行业务。如果先开事务再获取锁，锁等待期间会占用数据库连接

当前项目在这个场景下是 OK 的，因为删除队伍的并发场景少。但加入队伍那里我先取锁再执行业务逻辑（`tryLock` 在实际判断人数和插入之前），这个顺序是对的。

## 五、项目复盘

### Q14：这个项目你觉得自己最大的收获是什么？

**参考答案**（引导思考方向）：

1. **算法思维**：从暴力 O(N²) 到倒排索引 + TF-IDF，真正理解了"用空间换时间"和"索引加速检索"的思想——这和数据库索引、ES 倒排索引是同一个道理
2. **系统设计**：从单体架构出发，需要考虑缓存、分布式锁、会话共享、AI 集成，这些是真实生产环境会遇到的问题
3. **trade-off 意识**：MD5 vs Bcrypt、JSON vs 关联表、倒排索引 vs 编辑距离——每个选择都有代价，重要的是在具体场景下做最优决策
4. **全栈能力**：从后端业务逻辑到前端 Vue 交互，一个完整的闭环项目

### Q15：如果让你重新做这个项目，你会怎么设计？

**参考答案**：

1. **先做技术选型文档**：一开始直接开写，后面改了好几次（比如从编辑距离换到 TF-IDF、从 HashMap 缓存换到 Redis）。如果先想清楚数据量和查询模式，能省很多时间
2. **先写测试**：匹配算法的正确性应该用单元测试保证，而不是人工验证。比如构造已知标签的用户集，断言算法返回的 Top1 符合预期
3. **监控先行**：加 `micrometer` + `Prometheus`，对匹配接口的耗时和 AI 接口的成功率做监控，而不是靠"感觉"来判断性能
4. **配置外部化**：AI API Key 不应该在 yml 里明文存储，应该用环境变量或配置中心

### Q16：你觉得这个项目最大的不足是什么？

**参考答案**（按重要性排序，选 2~3 个说）：

**1. 匹配算法在大数据量下有瓶颈**

当前稠密向量 `double[V]` 在标签池扩大到千级别后，余弦计算会变成瓶颈。虽然已通过倒排索引召回将候选集缩小，但在热门标签场景下候选集仍可能很大。没有做过大规模压测。

> 改进：用稀疏向量（Map）替代稠密数组；用户上万时上 Elasticsearch 或向量数据库（Milvus）；离线预计算 + Redis 缓存匹配结果。

**2. 没有做 AB 测试验证 AI 推荐理由的效果**

AI 推荐理由到底是让用户更愿意组队了，还是只是装饰？没有数据支撑。

> 改进：对部分用户展示 AI 理由、部分展示规则理由，对比匹配点击率和组队转化率。数据驱动决策。

**3. WebSocket 聊天室为单机设计**

当前聊天室基于内存 ConcurrentHashMap 管理房间和 Session，如果多实例部署，消息无法跨节点广播。

> 改进：引入 Redis Pub/Sub 做跨节点消息广播，或迁移到 STOMP + RabbitMQ 的 WebSocket 方案。

**已解决的不足（之前版本存在的问题，改造后已修复）：**
- ✅ 自动化测试：已添加 JUnit 5 单元测试（MatchAlgorithmServiceTest 12 个用例）+ Mockito
- ✅ 性能监控：已接入 Micrometer + Prometheus + Grafana，覆盖 QPS/AI 成功率/缓存命中率
- ✅ 敏感信息硬编码：已全部改为 `${ENV_VAR}` 占位符，提供 application-example.yml 模板
- ✅ 缓存三大问题：已实现穿透防护（空值缓存）+ 击穿防护（Redisson 互斥锁）+ 雪崩防护（TTL 随机化）

### Q17：如果用户量从 40 人涨到 10 万人，你的系统哪里会先挂？

**参考答案**（展示瓶颈分析能力）：

**第一挂：`userService.list()` 全量查用户**

匹配接口每次都查全部用户到内存，10 万用户 × 标签 JSON 字段 ≈ 几十 MB 内存，GC 压力巨大，接口超时。

> 改进：加 Redis 缓存用户列表；匹配算法改为分批处理；加数据库索引 + 只查必要字段。

**第二挂：AI 接口 QPS 限制**

qwen-plus 有并发限制，10 万人同时点"智能匹配"，AI 接口直接被打爆。

> 改进：AI 推荐理由异步生成（消息队列），先返回匹配结果，推荐理由后续写回；相同标签组合的用户复用推荐理由（缓存）。

**第三挂：单机内存**

倒排索引、词汇表、所有用户向量全在 JVM 内存，用户多了 OOM。

> 改进：水平扩展 + Redis 做分布式缓存；匹配计算独立成微服务，按用户 ID 哈希分片。

---

### Q18：你的分布式锁在 Redis 主从切换时会不会有问题？

**参考答案**：

**会。** 当前用的是单节点 Redisson 锁，如果 Redis 是主从架构：

1. 客户端 A 在主节点拿到锁
2. 主节点宕机，锁的 key 还没同步到从节点
3. 从节点升级为新主，客户端 B 在新主上拿到同一把锁
4. A 和 B 同时认为自己持有锁 → 分布式锁失效

> 改进方案：用 Redisson 的 **RedLock（红锁）**——需要 N 个独立的 Redis 节点（N 是奇数），客户端必须在超过 N/2 的节点上成功加锁才算获取成功。或者直接用 ZooKeeper/Etcd 的 CP 一致性保证。

---

### Q19：项目里有没有 SQL 注入风险？怎么防的？

**参考答案**：

当前使用 MyBatis-Plus 的条件构造器（`LambdaQueryWrapper`），底层是参数化查询（PreparedStatement），天然防 SQL 注入。

但如果手写 MyBatis XML 用了 `${}` 而不是 `#{}`，就有注入风险。

> 改进：全局检查所有 mapper XML，确保没有 `${}` 拼接用户输入；加 SQL 注入拦截器做兜底。

### Q20：你的缓存如果被恶意请求打穿怎么办？（缓存穿透/击穿/雪崩）

**参考答案**：

项目已完整实现三大缓存问题的防护：

| 问题         | 现象                               | 当前状态  | 实现方案              |
| ------------ | ---------------------------------- | --------- | --------------------- |
| **缓存穿透** | 查不存在的 userId，每次都穿透到 DB | ✅ 已处理 | 空值缓存（TTL 5min），后续可直接命中空标记返回空页 |
| **缓存击穿** | 热点 key 过期瞬间大量请求打到 DB   | ✅ 已处理 | Redisson 互斥锁 + Double-check，获取锁失败线程降级返回空页 |
| **缓存雪崩** | 大量 key 同时过期，DB 瞬间压力暴涨 | ✅ 已处理 | TTL 加随机值错开（推荐缓存 120±30min，匹配缓存 10~20min） |

**实现细节**：
- 穿透：查询结果为空时缓存特殊标记 `EMPTY_PAGE`，TTL 3~5 分钟
- 击穿：Redisson `tryLock(3, 10, SECONDS)`，锁持有时间 10 秒，其他线程等待最多 3 秒后降级
- 雪崩：`ThreadLocalRandom.nextInt()` 给每个 key 的 TTL 加上随机偏移
- 额外的定时预热：每天 23:58 用 @Scheduled + 分布式锁为白名单用户预热缓存

### Q21：如果让你把这个项目部署到生产环境，还缺什么？

**参考答案**（展示运维意识）：

1. **CI/CD 流水线**：Git push → 自动编译 → 跑测试 → 构建镜像 → 部署
2. **日志采集**：ELK（Elasticsearch + Logstash + Kibana）收集分布式日志，方便排查问题
3. **健康检查**：Spring Boot Actuator + K8s liveness/readiness probe
4. **限流熔断**：Sentinel 限流，AI 接口加熔断（连续失败 N 次不再调用）
5. **数据库备份**：定时全量 + binlog 增量备份
6. **安全加固**：HTTPS、接口鉴权（JWT Token 替代 Session）、敏感数据脱敏
7. **压测报告**：JMeter 压测接口极限 QPS，知道系统容量
