## 三、简历项目描述（社招版 - 可直接使用）

### 项目名称：智配通 - AI 驱动的智能组队推荐平台

**技术栈**：Spring Boot 3.5 / Java 21 / MyBatis-Plus / Redis + Redisson / Spring AI Alibaba / WebSocket / Prometheus + Grafana / Docker

**项目描述**：独立设计并开发的全栈智能组队平台，解决用户"找不到合适队友"的痛点。系统基于自研多维度推荐算法为用户匹配最佳伙伴，并集成大模型生成可解释推荐理由，覆盖用户注册、标签匹配、组队协作、实时聊天、画像分析全链路。

**核心工作**（独立负责后端全部模块 + 前端页面开发）：

- **解决匹配性能瓶颈**：初期基于编辑距离的匹配算法在 2000 用户规模下耗时 5.5s，无法上线。自研 TF-IDF 向量化 + 倒排索引召回 + 余弦相似度精排方案，引入候选集剪枝将复杂度从 O(N²) 降至 O(C×V)，并设计多维度加权打分模型（标签 65% + 行为 20% + 互补性 10% + 协作评分 5%）；JMH 基准测试验证耗时降至 0.89s，**性能提升 6.16 倍**，且随用户量增长优势持续扩大

- **解决推荐可解释性问题**：纯算法推荐用户不理解"为什么推这个人"，信任度低。集成 Spring AI Alibaba + 通义千问大模型，为每条匹配结果生成 80 字内自然语言推荐理由；面对 AI 接口延迟问题（单次 ~200ms），采用 **JDK 21 虚拟线程池**并行调用 10 条结果 + 单条 3s 超时降级为规则理由，总耗时控制在 ≤ 3s，AI 失败时自动 fallback 且 Prometheus 告警

- **解决接口响应慢与缓存一致性问题**：推荐接口首次计算需 3~8s（含 AI 调用），用户重复请求体验差。设计 Redis 三层缓存防护体系 —— 空值缓存防穿透（TTL 3min）、Redisson 互斥锁 + Double-Check 防击穿、TTL 随机偏移 ±30min 防雪崩，缓存命中响应 ≤ 10ms；同时基于 **Spring ApplicationEvent** 事件机制实现队伍变更自动触发画像重算 + 缓存失效，保证数据一致性且业务模块零耦合

- **解决高并发超卖问题**：多人同时加入同一队伍时存在超卖风险（人数超过上限）。采用 Redisson 分布式锁 `tryLock(3,10s)` 串行化入队操作，锁内先查已加入人数再判断是否满员，finally 安全释放锁，经压测验证并发场景零超卖

- **构建全链路可观测性**：生产环境出问题时无法定位瓶颈。基于 Micrometer 自定义 6 项业务指标（匹配请求数、匹配耗时 P95/P99、AI 调用成功/失败数、缓存命中/未命中数），通过 Actuator 暴露 Prometheus 采集端点，Grafana 面板实时监控 QPS、AI 成功率、缓存命中率

- **容器化部署与生产加固**：Docker 多阶段构建（Maven 编译 → JRE Alpine 最小镜像），非 root 用户运行，JVM G1GC 调优；docker-compose 一键编排 MySQL/Redis/应用/Prometheus/Grafana/Nginx 共 6 个服务；Logback 分级日志（错误 60 天 + 全量 30 天），敏感配置全部环境变量注入

## 五、社招高频追问与应答（问题驱动风格）

### Q1：为什么不用 ES 做搜索/匹配？

> **选型决策**：对比了 ES 和内存方案。当前用户量 <1000，内存倒排索引完全够用。ES 引入后需要额外维护集群部署、分片策略、数据同步链路，ROI 不高。而且我的匹配算法（TF-IDF + 余弦相似度 + 多维度打分）是定制化的，ES 的 text similarity 不直接支持。如果用户增长到百万级，倒排索引的设计思想可以复用，平滑迁移到 ES。

### Q2：分布式锁怎么防超卖的？踩过什么坑？

> 加入队伍时多人并发，不加锁会出现"查人数未满 → 两人同时插入 → 超卖"。用 Redisson RLock 的 `tryLock(3,10s)`：等待 3s 获取锁，持有 10s。获取锁后先查已加入人数（Double-Check），再插入。finally 中 `isHeldByCurrentThread()` 只释放自己的锁，防止超时后被其他线程误释放。踩过一个坑：最初用 `lock()` 无限等待，导致 Redis 故障时线程永久阻塞，改为 `tryLock` 后加了超时降级。

### Q3：AI 推荐挂了怎么办？

> 三层容错设计：① 单条 `CompletableFuture.orTimeout(3s)` 超时自动降级为规则理由（"你和 XX 都擅长 Java，很适合一起协作"）；② 批量 `allOf.orTimeout(6s)` 整体兜底，超时后剩余结果用规则理由；③ Prometheus Counter 分别统计 AI 成功/失败次数，Grafana 面板展示成功率，失败率超阈值可配告警。实测 AI 降级后用户无感知，只是推荐理由从个性化变为模板化。

### Q4：虚拟线程在你项目里具体怎么用的？效果如何量化？

> AI 接口调用是典型 I/O 密集型（每次 ~200ms），需要为 10 条匹配结果并行调用。传统线程池每个线程 ~1MB 栈内存，10 个并行就是 10MB。我用 JDK 21 的 `Executors.newVirtualThreadPerTaskExecutor()` 创建虚拟线程池，内存仅几 KB/线程，I/O 等待时自动释放载体线程。效果：10 条并行 AI 调用总耗时从串行 ~2s 降至 ~200ms（取最慢一条），内存开销从 ~10MB 降至几十 KB。

### Q5：缓存一致性怎么保证？为什么用事件机制而不是直接调用？

> 直接调用（`profileService.calculate()`）会让 TeamServiceImpl 依赖画像服务和 Redis，违反单一职责。我用 Spring ApplicationEvent 解耦：队伍操作成功后 `publishEvent(TeamEvent)`，TeamEventListener 独立监听，同步重算画像 + 异步（`@Async`）清缓存。未来加通知、积分等只需新建监听器，核心代码零修改。这不是微服务专属——ApplicationEvent 是进程内事件，从 Spring 2.0 就有，单体项目用完全合理。

### Q6：你的监控是怎么做的？能发现什么问题？

> Micrometer 自定义 6 项指标 + Prometheus pull 采集（10s 间隔） + Grafana 可视化。核心价值：① 缓存命中率低于 80% 时说明缓存策略需要调优；② AI 失败率高于 20% 时触发告警，可能是大模型服务不稳定需降级；③ 匹配耗时 P99 超过阈值说明候选集过大需要截断。这些指标是我做方案优化时的数据依据。

### Q7：项目中遇到过最难的问题是什么？（社招必问）

> **AI 批量调用超时问题**。最初 10 条匹配结果串行调 AI，总耗时 10~30s，用户体验极差。第一次优化改为线程池并行，但 30 个用户同时请求会创建 300 个线程，OOM 风险。最终方案：JDK 21 虚拟线程池 + `CompletableFuture.orTimeout(3s)` 单条超时 + `allOf.orTimeout(6s)` 整体兜底 + 规则理由 fallback。上线后 10 条推荐总耗时稳定 ≤ 3s，超时率从 30% 降至 < 5%。

### Q8：如果流量增长 10 倍，你的系统扛得住吗？

> 当前架构做了几个预判：① 缓存命中率 >90% 的情况下 Redis 扛得住；② 匹配算法已用倒排索引 + 候选集剪枝，复杂度可控；③ AI 调用有限流（QPS=5）+ 缓存，不会打爆大模型接口。真正的瓶颈在候选集过大时（热门标签集中），需要加候选集上限截断（max 5000）或离线预计算。如果拆微服务，事件机制可平滑升级为 MQ。

### 用费曼法理解本项目的 8 个核心技术点

#### 1. 倒排索引 → 说人话

> 📖 **术语版**：构建 `Map<标签, Set<用户ID>>`，通过标签快速召回候选用户，将匹配复杂度从 O(N²) 降至 O(C×V)
>
> 🗣️ **说人话版**：就像你去图书馆找书，不是一本一本翻（全量扫描），而是先查索引卡片——"Java"这个标签对应第3、17、42号书（用户）。你只需要翻这几本，不用把整个图书馆翻一遍。**标签就是索引卡片，倒排索引就是提前帮你做好了卡片目录。**
>
> 🧒 **讲给小学生听**：假设全班50个同学，每个人有3个爱好标签。你想找到和你爱好最像的人。傻办法是拿你的标签和每个人一个个对比。聪明办法是先让班长统计："喜欢篮球的有张三、李四、王五"——这样你只需要在同样喜欢篮球的人里找，省了90%的时间。
>
> 💡 **一句话灵魂概括**：倒排索引 = 提前做好"标签→人"的速查表，匹配时不用全量扫描。

#### 2. 缓存穿透/击穿/雪崩 → 说人话

> 🗣️ **说人话版**：把Redis缓存想象成一家热门餐厅的**前台取餐窗口**。
>
> - **缓存穿透** = 有人一直点菜单上没有的菜（查不存在的userId）。前台每次都去后厨问，后厨累死。解决办法：在前台贴一张纸——"如果有人点XXX，直接告诉他没这道菜"（空值缓存）。
> - **缓存击穿** = 某道招牌菜刚卖完（热点key过期），瞬间100个人同时来点。前台只有一个人能进后厨催菜（互斥锁），其他人等着——等菜端出来，所有人都有了（Double-Check）。
> - **缓存雪崩** = 所有菜同时卖完（大量key同时过期），后厨瞬间爆炸。解决办法：给每道菜的过期时间故意错开——这道菜120分钟过期，那道菜140分钟过期，避免扎堆。
>
> 💡 **一句话灵魂概括**：穿透=查不存在的东西（空值拦截），击穿=热点过期瞬间（锁+等），雪崩=集体过期（时间错开）。

#### 3. 虚拟线程 → 说人话

> 🗣️ **说人话版**：传统线程像**出租车**——每接一个乘客就要一辆车，车很重（1MB栈内存），100个乘客要100辆车，停车场（内存）爆满。虚拟线程像**共享单车**——车很轻（几KB），乘客扫码骑走，等红灯时就放下车让给别人骑（I/O等待时释放底层线程），100个乘客只需要几辆真正的车来回调度就够了。
>
> 💡 **一句话灵魂概括**：虚拟线程 = 共享单车模式，轻量级 + 自动调度，I/O密集场景的神器。

#### 4. Redisson分布式锁 → 说人话

> 🗣️ **说人话版**：想象一个公共厕所，只有一个坑位。没有锁的话，两个人同时推门进去——事故。`synchronized` 只能管同一栋楼里的人排队，另一栋楼（另一个JVM实例）的人不知道这边有人。Redisson分布式锁就是在Redis（公共公告板）上贴一张纸条"厕所有人"——所有楼的人都能看到。看门狗机制就是：如果你蹲太久，自动帮你续一下纸条上的时间，防止纸条过期别人以为没人。
>
> 💡 **一句话灵魂概括**：分布式锁 = 跨服务器的"使用中"标识牌，Redisson帮你自动续期防超时。

#### 5. 余弦相似度 → 说人话

> 🗣️ **说人话版**：把每个用户的标签想象成空间中的一个箭头（向量）。你和另一个人的箭头越指向同一个方向（夹角越小），说明你们越相似。cos(0°)=1 表示完全一样，cos(90°)=0 表示完全不相关。编辑距离只比较"字符串像不像"，余弦相似度比较"方向对不对"——"Spring Boot"和"Spring Cloud"虽然字不同，但在标签空间里方向很近。
>
> 💡 **一句话灵魂概括**：余弦相似度 = 看两个箭头指向的夹角，角越小越相似。

#### 6. Spring事件机制 → 说人话

> 🗣️ **说人话版**：队伍有人加入后，需要做两件事：① 重算画像 ② 清缓存。如果直接写在加入队伍的代码里，就像每次做完饭还要自己洗衣服——职责混乱。事件机制就像**办公室广播**："XX加入队伍啦！"——画像部门听到广播自己更新画像，缓存部门听到广播自己清缓存。做饭的人只管做饭，广播一发，其他部门自动响应。未来加了"积分部门"，只需要接上广播线，做饭代码一行不用改。
>

```

### JVM 相关（结合虚拟线程追问）

#### Q9：你说用了 JDK 21 虚拟线程，它和 Go 的 goroutine 有什么区别？

> **面试官心理**：考察你是否理解虚拟线程的底层原理，而不是跟风用。

**参考答案**：

| 维度     | Java 虚拟线程                                                              | Go goroutine                     |
| -------- | -------------------------------------------------------------------------- | -------------------------------- |
| 调度模型 | JVM 调度到 OS 线程（M:N）                                                  | Go runtime 调度到 OS 线程（M:N） |
| 栈内存   | 动态伸缩（初始几KB，按需增长）                                             | 动态伸缩（初始 2KB）             |
| 阻塞处理 | I/O 阻塞时自动 unmount 载体线程                                            | I/O 阻塞时自动让出 P             |
| 抢占方式 | 在安全点（safepoint）检查                                                  | 基于信号的抢占（1.14+）          |
| 关键区别 | Java 虚拟线程是 **JDK 层面** 实现，Go goroutine 是 **语言运行时** 原生支持 |

**一句话**：Java 虚拟线程让你在传统线程模型上无痛迁移，Go goroutine 是语言级内置。

---

#### Q10：虚拟线程有什么缺点？什么场景不适合用？

**参考答案**：

1. **计算密集型不合适**：虚拟线程的优势是 I/O 等待时释放载体线程。如果是纯 CPU 计算（如排序 100 万条数据），虚拟线程反而增加调度开销，用传统线程池更好。
2. **synchronized 会 pin 住载体线程**：JDK 21 中，虚拟线程执行 `synchronized` 块时不会释放载体线程——这是一个已知限制。所以我的代码中 Alibaba Spring AI 底层如果有 `synchronized`，虚拟线程的优势会打折扣。JDK 24 中已修复此问题。
3. **ThreadLocal 内存泄漏风险加大**：虚拟线程数量可能成千上万，如果每个都存 ThreadLocal 数据，内存占用惊人。建议用 `ScopedValue`（JDK 21 预览）替代。

#### Q12：你的项目里 user 表的 tags 是 JSON 字段，如果要查"拥有 Java 标签的所有用户"，怎么写 SQL？性能如何？

CREATE INDEX idx_tags_flat ON user(tags_flat);
```

2. 上 Elasticsearch（标签数上千、用户百万级时）
3. 关联表方案（user_tag 表，支持精确 SQL 查询）

#### Q13：你项目里用了 MyBatis-Plus 的 `LambdaQueryWrapper`，如果手写 SQL 怎么防止 SQL 注入？`#{}` 和 `${}` 的区别？

**参考答案**：

| 符号  | 原理                                                     | 安全性        | 使用场景                     |
| ----- | -------------------------------------------------------- | ------------- | ---------------------------- |
| `#{}` | PreparedStatement 参数化，预编译 SQL 后用 `?` 占位再设值 | ✅ 安全       | 99% 的查询参数               |
| `${}` | 直接字符串拼接进 SQL                                     | ❌ 有注入风险 | 仅用于动态表名/列名/ORDER BY |

**示例**：

```xml
<!-- 安全：用户输入被当作参数值，不会被当作SQL执行 -->
SELECT * FROM user WHERE username = #{username}

<!-- 危险：用户输入直接拼进SQL，可以注入 -->
SELECT * FROM user WHERE username = '${username}'
-- 用户输入 ' OR '1'='1' -- → 导致查出所有用户
```

**MyBatis-Plus 的安全性**：`LambdaQueryWrapper` 底层也是 PreparedStatement，天然防注入。项目中所有手写 XML 需要检查是否有 `${}` 直接拼接用户输入。

> "虽然我的项目没有用 RAG，但 AI 推荐理由生成本质上是'检索用户信息 → 生成推荐语'的模式。如果把用户画像、组队历史也作为 Prompt 上下文传入，就是简化版的 RAG。未来如果要做一个智能客服（用户问'谁适合我的项目'），就需要 RAG 检索团队的描述、用户技能等信息。"

### 3. AI Agent

**基本概念**：能自主规划、调用工具、执行多步任务的 AI 系统。

**和你的项目的关联**（可说）：

> "我的项目目前是'工具型'AI 调用（输入→输出），不是 Agent。但如果未来要让 AI 帮用户自动组队——'帮我找一个擅长前端、周末有空的队友并发出邀请'——就需要 Agent 的三要素：Planning（拆解为搜用户→筛选→发邀请）、Tools（调用搜索接口、发邀请接口）、Memory（记住用户偏好）。"

### 4. 监控 vs 可观测性

**基本概念区分**（面试常问）：

- **监控（Monitoring）**：你知道什么会坏，设置了告警（如 AI 失败率 > 20% 告警）
- **可观测性（Observability）**：你不知道什么会坏，但系统能让你在出问题时快速定位（如通过 TraceId 串联一次请求的全链路）

**你在项目中的实践**：

> "我的项目目前是监控阶段——6 项自定义指标 + Prometheus + Grafana 告警。如果要做到可观测性，需要加 OpenTelemetry 做分布式链路追踪，一次匹配请求从 Controller → Service → 缓存 → AI 调用的每一步耗时都能看到。"
